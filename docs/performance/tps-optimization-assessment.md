# TPS Optimization Assessment

## Executive Summary

Teleno can improve transaction throughput substantially without changing the
Koinos protocol or replacing its current sequential execution architecture.
The first private benchmark found that RPC admission, load-generation
behavior, runtime configuration, and resource contention limited the measured
result before the node reached a demonstrated protocol ceiling.

The strongest valid run admitted all 1,000 submitted KOIN transfers at
approximately **451 transactions per second**. A separate analysis of the
corresponding producer blocks found that the 1,000 transactions were packed
into 11 blocks over 5.55 seconds between the first and last non-empty block,
or approximately **180 transactions per second while those blocks were
flowing**. Neither figure is a mainnet TPS claim: the test used one local
machine, loopback networking, an unusually fast private PoB chain, and a
single simple transaction type.

The immediate conclusion is that Teleno should optimize and re-benchmark the
current architecture before considering a protocol-level execution redesign.
The likely gains are meaningful, but current-architecture optimization alone
should not be expected to produce Solana-class throughput.

## What TPS Means

Throughput comparisons must keep different measurements separate:

- **Offered TPS** is the rate generated by the benchmark client.
- **Admission TPS** is the rate of successful
  `chain.submit_transaction` responses.
- **Block-inclusion TPS** is the rate at which accepted transactions appear in
  produced blocks.
- **Witness-detection TPS** includes the time required for an independent node
  to receive and inspect those blocks.
- **Finalized TPS** requires the transactions to reach the chain's defined
  irreversibility threshold.

Admission TPS measures the RPC, validation, and mempool path. It does not prove
that consensus can sustain the same rate. Block inclusion is closer to chain
capacity, but it still does not measure geographically distributed finality.

## Benchmark Environment

The 2026-07-12 benchmark used:

- Teleno `1.2.0-dev.0` at commit
  `a2db3d5d034aec4b12ab6a94f73d98ad7041f802`;
- an Apple M2 with 8 logical CPUs and 8 GiB of RAM;
- one producer, one seed, and one independent observer on the same machine;
- loopback RPC and P2P connections;
- a disposable private PoB genesis;
- one KOIN transfer per transaction;
- distinct pre-funded private-testnet payers, each starting at nonce 1;
- a producer resource upper bound of 90%;
- a private-chain compute limit of 100,000,000 units per block.

No public testnet or mainnet transactions were submitted.

The default 500-transaction saturation run rejected 178 requests with
`JSON-RPC session limit reached`; another 56 client connections ended with a
broken pipe. The tuned configuration raised the private producer's JSON-RPC
session limit from 4 to 64 and disabled the per-account pending-transaction
limit. The latter was not expected to bind because the valid workload used
distinct payers, but the two changes were not isolated in separate runs. The
tuned configuration eliminated all rejections in the following 500- and
1,000-transaction runs.

The two 1,000-transaction runs converged near 451 admission TPS despite
different offered-rate settings. This is the observed ceiling of this test
configuration, not yet a proven ceiling of `teleno_node`.

## Account Nonce Control

An initial control submitted ten transactions concurrently from one payer
with sequential nonces. Only the first transaction was accepted because later
requests arrived before the next pending nonce became visible. That result
measured account nonce serialization rather than node capacity and is excluded
from throughput conclusions.

The valid workload used independent payers so every transaction could be
validated concurrently with nonce 1. Realistic future workloads should include
both independent-account traffic and intentionally contended accounts.

## Block Resource Findings

The final 1,000-transaction workload appeared in 11 blocks, with a maximum of
100 transactions in one block. Across those blocks it consumed:

- 820,224,836 compute bandwidth, approximately 820,225 per transaction;
- 315,114 network bandwidth, approximately 315 bytes per transaction;
- 35,000 disk storage, 35 bytes per transaction.

The private chain exposed limits of 100,000,000 compute, 1,048,576 network,
and 409,600 disk per block. With the producer configured to stop near 90% of a
resource limit, compute was the binding resource for this transfer workload.
Network and disk limits had substantial unused capacity.

The independent witness found all 1,000 transactions. Its end-to-end detection
rate was approximately 49 TPS because it also had to catch up across hundreds
of blocks created by the unusually fast private producer. That value measures
this witness path, not producer execution capacity or mainnet finality.

## Improvements Within the Current Architecture

The following work does not require changing Koinos transaction semantics or
introducing parallel state execution.

### Benchmark and RPC Path

1. Replace per-request HTTP connections with persistent keep-alive
   connections and connection pooling.
2. Use a native or asynchronous load generator capable of proving that the
   client is not the bottleneck.
3. Tune the JSON-RPC session limit and worker count independently.
4. Add explicit overload queues and backpressure instead of closing excess
   connections.
5. Measure JSON parsing, Protobuf conversion, request dispatch, and response
   serialization separately.

### Transaction Admission

1. Parallelize signature verification, hashing, decoding, and other
   transaction-independent checks.
2. Reduce shared locks between JSON-RPC, chain validation, and the mempool.
3. Batch event publication and avoid synchronous work after a transaction has
   already been accepted.
4. Profile pending nonce and pending resource accounting under independent and
   contended payer workloads.
5. Separate admission capacity from P2P broadcast capacity in both metrics and
   execution paths.

### Execution and Storage

1. Profile system-contract and WASM execution for the exact operation mix.
2. Improve compiled contract and frequently read state caches.
3. Reduce repeated serialization and hashing between admission and block
   application.
4. Batch compatible RocksDB writes and tune write buffers, background jobs,
   and cache allocation for sustained block application.
5. Move non-consensus indexing and diagnostics away from critical transaction
   and block paths.

### Operational Test Configuration

1. Run the producer, load generator, seed, and witness on separate machines.
2. Use release logging rather than debug logging during performance runs.
3. Record CPU saturation, per-thread utilization, memory, disk latency,
   network throughput, mempool depth, and block resource consumption.
4. Repeat each matrix row and report median, dispersion, and thermal state.
5. Validate the same build on representative macOS and Linux hardware.

## Current-Architecture Limits

Optimizing the admission path can raise RPC TPS without increasing the number
of transactions that fit into a block. Sustained chain throughput remains
bounded by:

- canonical transaction size;
- compute and disk cost per operation;
- block resource limits;
- average block interval;
- sequential state-transition execution;
- block propagation and validation time on the slowest acceptable validator;
- finality and fork behavior.

Block resource limits can be raised without redesigning transaction execution,
but only after a geographically distributed network proves that representative
validators can receive, validate, persist, and relay larger blocks within the
required interval. Increasing one producer's local limits cannot independently
increase mainnet throughput.

## Where an Architectural Redesign Begins

The current architecture can parallelize preprocessing, signature checks, and
other work that does not mutate shared state. General parallel transaction
execution is different. It would require deterministic conflict handling,
such as:

- transactions declaring their read and write sets;
- deterministic account or state locking;
- optimistic parallel execution with deterministic conflict replay;
- a redesigned concurrent state backend and scheduler;
- protocol and compatibility rules understood by every validator.

That work is closer to a new execution architecture than a normal Teleno
optimization. It should be considered only after profiling demonstrates that
sequential state execution, rather than admission, contracts, storage, or
block configuration, is the dominant remaining constraint.

## Recommended Next Benchmark

The next iteration should use a multi-host private network and run this matrix:

1. persistent-connection admission without broadcast;
2. admission with P2P broadcast;
3. producer inclusion at mainnet block cadence and resource limits;
4. independent witness inclusion;
5. irreversible-finality measurement;
6. simple transfers, contract calls, mixed operations, independent payers, and
   contended payers;
7. default and tuned RPC/chain worker configurations.

The immediate objective is not to publish a larger TPS number. It is to
identify the first resource that saturates, remove that bottleneck without
protocol divergence, and repeat until block execution or propagation becomes
the demonstrated limiting factor.

## Conclusion

The current Teleno architecture has meaningful optimization headroom. The
benchmark already demonstrated a large improvement from correcting the RPC
session bottleneck, and several client, admission, execution, storage, and
operational variables remain unisolated.

Current-architecture work should therefore continue before considering a
parallel execution redesign. It can plausibly deliver substantial gains, but
Solana-class throughput would require deeper changes to execution,
state-conflict management, block timing, propagation, and validator hardware
assumptions.
